Developer workflow:

1. `npm run questions:audit` previews current source coverage. `npm run questions:generate -- --dry-run` never writes, even combined with --apply.
2. `npm run questions:generate -- --apply` saves DRAFT candidates and their manifest. Re-running identical sources keeps IDs and versions; changed immutable content/source gets a new version. Keep generated files in version control so another developer retains version history.
3. `npm run questions:validate` regenerates expected content and rejects changed sources, answer/distractor/template/mapping mismatches, duplicates and invalid Arabic references.
4. `npm run questions:import-generated -- --apply` imports only validated versions into development. It batches lookups/inserts, does not delete, and never overwrites existing review/publication/quarantine state. Re-running is safe. --dry-run prevents database writes/connections in this generator CLI.
5. Publication is separate. A real qualified reviewer may approve exact versions in curated question-bank.json; after technical validation use `npm run questions:publish -- --human-review --apply`. The configured reviewer and approval evidence must exist. Alternatively, source-approvals.json can pin the exact sourceVersion and questionHashes from a genuinely reviewed source/transformation manifest, with trusted reviewer identity/date/evidence; `questions:publish -- --approval=<id> --apply` then considers only those exact versions. No source approval is supplied or inferred by the generator. SOURCE_VERIFIED never invents a human question review record.

An import cannot withdraw an already published version. Use the guarded internal quarantine CLI below; corrections need a new immutable version. Suspended versions cannot be published. Release requires existing valid publication provenance; otherwise keep the held version and approve a corrected new version. Preserve the hold rather than weakening it for convenience.

The owner-authorized development path is distinct from expert source verification: `REPOSITORY_DETERMINISTIC` records the real authorization, its registration time, environment, source file digests and exact immutable question hashes. Runtime `repositoryVerified` accepts only those versions outside NODE_ENV=production; `sourceVerified` remains false without qualified source review. Reproduce this approved publication with `npm run questions:publish -- --approval=owner-development-2026-10-26-5323ec44 --apply`. Generation/import never manufacture a new authorization or extend this one to changed content. Bulk publication locks every selected row and validates all before a single update; one suspended/invalid version aborts the batch. No fake human review is recorded. User reports, quarantine and historical scores keep their existing protections.

## User reports and internal review

POST /api/v1/questions/:questionId/feedback accepts a bounded category/description/version and requestId plus either the owner's submitted attemptId or a signed post-answer guest receipt. It stores no IP/device fingerprint or anonymous account. Reports do not change keys, scores, completion or publication. Serious Quran text/reference/highlight reports get HIGH review priority; report volume never automatically quarantines content. Public reads/status changes do not exist.

The CLI is the internal authorization boundary: local OS access plus a privileged development database role, never an HTTP admin bypass. It refuses production configuration. `npm run questions:feedback -- list --status=OPEN` lists at most fifty reports, optionally filtered by --question and --category. Review uses `review --id=<report-uuid> --status=IN_REVIEW|RESOLVED|REJECTED --actor=<operator> --note=<evidence> --apply`. Resolved/rejected need a note; the stored actor includes the actual database role. Suspend/release use `suspend|release --id=<question-uuid> --actor=<operator> --note=<reason> --apply`. Without --apply, or with --dry-run, mutations are only previewed. No app reviewer account or admin dashboard is fabricated.

Feedback rows retain the immutable version/snapshot/provenance. Quarantine retains its operator, reason and release details; published historical results remain readable. The flag is excluded from the immutable content hash so moderation does not rewrite history. No automatic publication, auto-correction, background scheduler or production migration is included.

Use the `QuestionContent` schema in `src/modules/quiz/question.types.ts`. Questions without an applicable explicit publication authorization remain DRAFT. Qualified review is still needed to claim scientific approval: verify wording, correct answer, plausible distractors, explanation, sources, and alignment with the existing lesson. Record the reviewer's identity, qualification and independently checkable review evidence in the trusted registry, then the specific approval evidence/date on each version. The registry is an operator trust boundary, never a public endpoint.

Identification references use the exact reader corpus and UTF-16 grapheme boundaries. Supply edition SHA-256, verse SHA-256, annotation ID and rule ID; never copy offsets from `quran-full.json`. Technical integrity does not prove scientific validity.

Run `npm run questions:check` for the curated file, review provenance, then `npm run questions:import` for initial curated versions. Import preserves immutable version content and never deletes, demotes or promotes existing records automatically. Corrections require a new UUID and increased contentVersion under the same stableId. Quarantine versions explicitly with the internal CLI. Old submitted results retain snapshots; active attempts with held content cannot be graded. Restart the API after trusted-registry changes.

Each lesson needs at least seven distinct eligible published questions. Include both types when the lesson has supported annotations; theory-only lessons use actual lesson facts without invented annotations. Target fourteen for retry variety. Duplicate/conflicting content is excluded by the runtime gate. Do not import synthetic fixtures from `test/` into the application schema. The conflicting upstream rule iqlab-noon.1 is excluded from generation; the reader source assets remain unchanged.

Runtime deployments must include `content/reviewers.json`, `content/source-approvals.json`, the shared catalogue/feedback category JSON and the unchanged reader corpus at `../web/src/data/tajweed-index.json` and `../web/public/data/tajweed/`, or set `QUIZ_CORPUS_INDEX` and `QUIZ_CORPUS_DIRECTORY` to equivalent mounted assets. Production Detective additionally requires `QUIZ_CHALLENGE_SECRET` (at least 32 random bytes encoded as a string, shared by API instances); otherwise Detective stays unavailable. These paths are content assets, not a dependency on frontend application code. Guest report receipts use a separate HMAC domain under that key; authenticated reports use owned submitted attempts.
